# AI 协作工作流（可移植）

从真实项目里提炼的。**重点不是「怎么让 AI 写代码」，是「怎么让它的产出可信」。**
下面每一条都对应一次实际翻车，不是通用建议 —— 通用建议没用，坑才会重复踩。

---

## 0. 一句话

**能跑就别读，能读就别猜；判据本身要验；不可逆的动作先读再动。**

---

## 1. 接手一个项目

- **能用读代码回答的，不要铺多个 agent 并行去查。** 一次 fan-out 的 token 成本
  常常超过直接把关键文件读一遍。
- 先分清两类信息：**「这个项目的事实」** 和 **「放到哪都成立的规律」**。
  前者进项目记忆，后者才值得进这份工作流。
- **先找可运行的验证入口**（测试、冒烟脚本、lint）。有就先用它建基线；
  没有就先造一个 —— 但造完必须真跑（见 §3.8）。
- 遇到「看起来像 bug」的现象，先确认**不是环境造成的假信号**（见 §3.6）。

---

## 2. 记忆怎么写才有效

写**下次会用到、且从代码里看不出来**的：

- ✅「main 是压缩快照，本地完整历史分支含密钥，绝不能推」—— 不读完所有历史不会知道
- ✅「ratio 字段存的是百分数，再乘 100 就是 bug」—— 踩过才知道
- ❌「项目用 FastAPI」—— 代码里写着
- ❌「今天修了 XXX」—— 只在当次对话有意义

三条硬要求：

1. **写清触发条件**（什么情况下该想起它），而不只写结论
2. **指向具体位置**（文件、字段名），但注明「可能过时，用前先核对」
3. **过时了就删** —— 不要留一堆互相矛盾的旧条目，那比没有更难用

---

## 3. 验证 —— 最容易自欺的一环

### 3.1 真跑 > 读代码

「读了一遍觉得对」和「跑过了」之间的差距，大到不像同一件事。
典型漏网：媒体查询的先后顺序、错误分支、并发、跨刷新恢复、导出产物。

### 3.2 判据本身要验

**最危险的不是没有判据，是判据写反了** —— 它会给出一个看起来精确的错误数字。

> 真实案例：`ok = got in expect`。Python 里 `None in []` 是 `False`，
> 于是所有「不该调用工具」的用例即便表现完全正确也被判错，
> 准确率从 78% 被压成 56%，而且这个数字看起来非常可信。

→ 任何打分/断言写完，先拿一个**已知答案**的样例试它。

### 3.3 假通过

兜底逻辑会把「失败」悄悄变成「通过」：

```python
area = res.get("total_disaster_area_mu") or 0   # 字段名写错 → None → 0
assert area <= 120                              # 0 <= 120 → 通过
```

→ 先断言字段**存在且是数值**，再比大小。

### 3.4 测试脚本自己的 bug，会被误读成「应用的 bug」

高频三件套：猜错字段名、猜错响应的嵌套层级、猜错 DOM 选择器。
症状是「失败」看起来像真问题，于是去改根本没坏的代码。

→ **断言之前先把真实结构打印出来看**，不要凭印象写断言。

### 3.5 测试要隔离 + 自清理

- **随机化输入**，避免命中缓存，导致「改了但看起来没生效」
- 用**临时目录**，不要污染项目
- 删东西要用**点名**的接口（`DELETE /x/{id}`），
  绝不用**清空**的接口（`DELETE /x`）
- 跑完复查：留下的数据集应与跑之前**完全一致**

### 3.6 环境陷阱（会给出完全错误的信号）

| 现象 | 真因 |
|---|---|
| 拦截请求不生效 | 页面注册了 Service Worker，SW 发出的请求**绕过** `page.route`，得用 `context.route` |
| 改了全局对象但没效果 | `add_init_script` 里改 `window.xxx` 在部分宿主里静默失效；改成**替换模块导出的方法** |
| 输出乱码 / 报编码错 | 控制台是 GBK，`print` UTF-8 文本会炸 —— 而报错看起来像「功能失败」 |
| 日志文件永远是空的 | 启动时有别的组件（迁移工具、框架）接管了 root logger |

### 3.7 静默降级 —— 不报错 ≠ 正常

最贵的一类 bug：**行为是对的，错在不吭声**，于是用户看到一个看起来正常、
实则有损的界面。判断标准：

> 这个失败会不会让界面「看起来正常、但结果/状态是错的」？会 → 必须说出来。

排查手段：全局搜空的 `catch {}` / `except: pass`，逐个问「这里吞掉的是什么」，
再区分「有意忽略且合理」和「会藏问题」。

### 3.8 日志要亲眼确认它落了盘

别假设 `logger.info(...)` 会出现在文件里。

> 真实案例：日志文件恒为 0 字节，且**不报任何错**。根因是启动顺序 ——
> 应用先配好 handler，之后迁移工具用 `fileConfig` 把 root 的 handler
> 整个替换了，文件 handler 消失、级别被抬到 WARNING。

→ 写一行探针，看文件大小变没变。顺带：查一条「本该出现的告警」在不在，
比读代码更能证明日志链路是通的。

## 4. 不可逆操作

- **要跑一个会写/删的脚本之前，先读它。**

  > 真实代价：一个冒烟脚本里写了 `DELETE /history?record_id=99999`，
  > 而单条删除的真实路径是 `/history/{id}` —— `DELETE /history` 是**清空全部**。
  > 它返回 200，所以这一项还「通过」了。195 条本地记录没了。

- **先冻结现场再排查**：停掉写入方、把数据文件复制一份，然后再研究。
  晚一步，现场就被覆盖了。
- **对恢复难度要有正确预期**：数据库里的「删除」不一定抹掉字节，
  但也**不能指望捞得回来**。实测：freelist 上 25 页全零，全文件搜不到一条特征串，
  且没有备份 → 确定不可恢复。早点确认「没救」，比反复尝试省时间。
- **删除要「点名」**。不要用「我认为这些是垃圾」当理由批量删 ——
  只有明确指向的对象才删，其余列出来问。
- **改共用工具的谨慎程度要高于改业务代码**：影响面不一样。

## 5. 提交与发布前

- **扫密钥，含历史。** 新提交干净 ≠ 旧提交干净。
- **不确定的不要提交。** 拿不准就单独列出来问。
- 分清「对外发布的干净快照分支」和「本地含敏感信息的完整历史分支」，
  推之前确认推的是哪个。
- **别把无关目录顺手带上**（工具目录、内部笔记、参考资料）。
- 提交信息写**为什么**，不写「改了什么」—— 后者看 diff 就知道。

---

## 6. 沟通

- **短问短答**，长度跟着问题走。
- **不加「另外还有几件事」的清单尾巴。**
- **悬留事项只提一次**，对方不接就丢掉。
- 报**结论和进度**，不要报过程。
- 同一会话里已确认的事实**不重复验证**。
- **失败了如实说**，不要用「基本完成」这类说法糊过去。

---

## 7. 换项目时，先做这四件

1. **写 `CLAUDE.md` / 约定文件**：项目结构、命名习惯、禁忌
2. **先把 `.gitignore` 写好**：`.env`、数据、产物、本地配置
3. **准备一个能跑的验证入口**（`pytest` + 冒烟脚本），并在 README 里写明
   每个脚本**覆盖什么、要不要先起服务、花不花钱（LLM 调用）**
4. **把「不能推的分支」「哪些目录别外发」写进记忆** —— 这类约束不写下来，
   下次一定会踩

---

## 附：这份工作流自身的用法

- 新项目开始前通读一遍，重点是 §4 和 §5（那两节的代价最高）
- 每次「发现一个我以为对但其实错了的东西」时，回来看它该进哪一节
- **能进这里的只有「换个项目还会成立」的条目**，项目专属的写进那个项目的记忆
