# Agent：两条通道与工具说明

这个系统的「AI Agent」不是一个东西，**是两条独立实现、权限与原理都不同
的通道**。这份文档讲清它们的差别、各自能做什么、以及为什么这么设计。

> 系统整体结构见 [ARCHITECTURE.md](ARCHITECTURE.md)。

---

## 一、为什么有两条通道

| | **工具通道** | **浏览器通道** |
|---|---|---|
| 端点 | `POST /agent/execute-tools` | `POST /agent/execute` |
| 原理 | 模型用 **Function Calling** 直接调服务层 | 模型**驱动真实 Chrome** 操作前端 |
| 权限 | **登录即可** | **仅管理员** |
| 限流 | 10 次/分钟 | 3 次/分钟 |
| 前端切换 | 面板上的「工具 / 浏览器」开关 | 同 |

### 权限为什么不一样

这是本项目里一处值得说明的**刻意设计**（理由写在 `routers/agent.py` 的
docstring 里）：

> 浏览器通道会**以管理员身份**驱动真实浏览器操作前端，属高权限功能 ——
> 此前仅要求登录（任意注册用户即可调用），现限定管理员。
>
> 工具通道权限刻意低一档：这条通道**全程以调用者本人的身份执行**，不启用
> 管理员旁路，没有 Chrome、没有可执行任意 JS 的会话，**能做的事与用户
> 自己点界面完全相同**，因此不构成提权。

一句话：**浏览器通道是「替你操作」，工具通道是「替你点按钮」。** 前者需要
管理员是因为它拿的是管理员会话；后者不需要，因为它越不了权。

### 浏览器通道的额外代价

驱动真实浏览器意味着：要起 Chromium 子进程、要处理信号接管
（`enable_signal_handler=False`，否则 Windows 上 `os._exit(0)` 会直接杀掉
uvicorn）、要防进程泄漏。所以它的限流是 3 次/分钟，而不是工具通道的 10 次。

## 二、工具通道的 7 个工具

这是给模型的完整能力清单（`tool_agent_service._tool_schemas`）：

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `list_models` | 列出**真正可用**的检测模型 | 挑模型前必须先调它，不要凭空猜模型名 |
| `run_detection` | 对一对双时相影像跑变化检测，返回变化比例与像素数，**并写入该用户的检测历史** | 影像路径必须是附件清单里的，参数做**逐字符白名单比对** |
| `list_detections` | 分页列出**当前用户自己的**检测历史 | 1~50 条，可按模型过滤 |
| `get_detection` | 按 ID 取一条记录的完整统计 | — |
| `assess_disaster` | 对一条记录做受灾定损：按置信度分四级算受灾面积、测经济损失 | **要求该记录带概率图**；模型对比建的不带，会明确报错 |
| `list_series` | 列出多时相序列（名称、地块、期数） | 趋势查询需要 ID，而用户通常只说名字，所以要先调它 |
| `get_series_trend` | 取序列的变化速率与趋势：拟合斜率、R²、突变点、被剔除期次说明 | 用来回答「这几年变化快不快」 |

**注意 `run_detection` 会写数据。** 它不是只读工具 —— 调用一次就在用户的
检测历史里留下一条记录。设计提示词时把这点告知了模型。

## 三、系统提示词的设计

`tool_agent_service.SYSTEM_PROMPT` 一共 6 条规则，每条都在防一类具体的失败：

| 规则 | 防的是什么 |
|---|---|
| 先想清楚要什么再选工具，不要臆造参数 | 模型编造不存在的参数名 |
| 附件路径**已在下方列出**，直接填，不要自己编造或改写形式 | 路径被"美化"成 `./xxx` 或 `file://` 后过不了白名单 |
| 不确定有哪些模型时**先调 `list_models`** | 猜模型名 → 调用失败 |
| 工具报错时**原样转述，不要反复重试同一个调用** | 模型陷入重试循环，烧钱且拖时间 |
| 拿到结果后**简洁汇报关键数字**，不要罗列原始 JSON | 把大段 JSON 倒给用户 |
| **只能看见当前用户自己的数据**；查空就如实说没有，不要推测 | 越权 + 幻觉编造数据 |

最后一条尤其重要：**「查不到」和「没有数据」必须分清**，不能让模型用
推测填补空白。

## 四、附件机制

用户可以在 Agent 面板里上传影像，作为「让 Agent 跑一次检测」的输入。

**为什么不直接传文件给模型**：模型不需要看影像内容，它只需要**路径**去调
`run_detection`。所以流程是：

```
上传 → 落盘到临时目录 → 路径清单拼进提示词 → 模型把路径填进工具参数
                                                      ↓
                                     服务端做逐字符白名单比对（防路径穿越）
```

附件清单的格式由 `agent_common.attachment_lines` 统一生成（两条通道共用，
且**测试的正则依赖这个格式**）。措辞按通道不同：工具通道必须点名
「不得改写」，因为要做白名单比对；无附件时也要明说「没有」，否则模型会去
猜路径然后被拒。

## 五、循环控制与预算

| 机制 | 值 | 作用 |
|---|---|---|
| `MAX_TOOL_ROUNDS` | 8 | 工具循环轮次上限。每轮是一次完整模型往返，放开会让一次请求拖到几分钟；正常任务 2~3 轮收敛 |
| `MAX_TOOL_RESULT_CHARS` | 4000 | 单次工具结果回灌给模型的字符上限，防列表类结果撑爆上下文 |
| `_LLM_TIMEOUT` | 120s | 单次模型调用超时 |
| 端点限流 | 10/min（工具）· 3/min（浏览器） | — |
| **每日调用预算** | 默认 500 | `core/llm_budget.py`。见下 |

### 为什么还要一道按天的闸

上面这些**全是按请求**的。限流按分钟算 —— 一个每 20 秒发一次的循环，
在它放开后一天能跑掉几千次调用，**而且不会有任何报错**，直到额度见底。

这个项目的 LLM key 常与开发者的其他用途共用同一份额度，所以额外加了
一道按天累计的闸（`LLM_DAILY_CALL_LIMIT`，默认 500，设 0 关闭）。
超了直接拒绝，报错信息明确指向「有代码在循环调用」。

局限（知道就好）：计数器在进程内存里，重启归零，多 worker 各算一份。

## 六、模型选型的硬约束

Agent 用的模型必须**同时**满足三项，缺一不可：

| 要求 | 为什么 |
|---|---|
| **视觉** | 浏览器通道每一步决策都基于页面截图 |
| **Function Calling** | 决策循环依赖结构化的 `tool_calls`。只回散文的模型跑不动（`qwen-vl-plus` 就是这样被淘汰的） |
| **结构化输出** | 见下 |

### 一个容易踩的坑：`json_schema` vs `json_object`

`browser_use` 库的 `ChatOpenAI` 会发
`response_format={"type":"json_schema"}`，而 **DeepSeek 对该类型返回 400**。
所以接 DeepSeek 必须换成同库的 `ChatDeepSeek`（它发 `json_object`）。

**这不是风格选择，是必需。** 而且 `ChatDeepSeek` 的参数表与 `ChatOpenAI`
不同 —— 它**拒绝未知关键字**，原来传的 `max_retries` / `reasoning_effort` /
`dont_force_structured_output` 都得去掉，否则直接 TypeError。

当前默认模型是 `deepseek-v4-flash`（三项实测都支持）。
**不要用 `deepseek-v4-pro`** —— 它不接受图片输入（传给它的图根本没进
`prompt_tokens`，模型自己会回「我无法查看这张图片」）。

## 七、还没有的

- **意图解析准确率**：Agent 是自由对话，没有「意图」这个概念，因此
  **无从度量它做得有多好**。要度量得先定义意图空间，再建指令测试集。
- **对话与图层联动**：说「显示 3 号地块」，地图不会动 —— Agent 页与地图页
  是分开的两页。
