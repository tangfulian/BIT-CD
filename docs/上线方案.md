# 上线方案与验证

> **本文的性质**：一份**可执行的上线方案 + 验证清单**。
> 其中「本地等效验证」是我实际跑过的结果；「生产环境验证」需要你在服务器上执行后填写。
> 两者的区别见 §6.1。

---

## 1. 适用范围

单机部署（1 台 Linux 服务器 + Docker），面向演示、试运行与中小规模使用。
不适用于多副本、高并发场景 —— 当前架构是单实例、SQLite、本地文件存储。

---

## 2. 环境要求

| 项 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Ubuntu 22.04（其它 Debian 系亦可） | `deploy.sh` 按 Ubuntu 写 |
| 权限 | root | 要装 Docker、写 `/opt` |
| 磁盘 | ≥ 10 GB | 镜像约 4 GB（含 torch 与 Chromium）+ 权重 + 结果文件 |
| 内存 | ≥ 4 GB | Agent 的 Chromium 需要；`shm_size` 已设 1 GB |
| 网络 | 能访问 GitHub、PyPI（构建期） | 构建时拉代码与依赖 |
| GPU | **非必需** | 镜像装的是 CPU 版 torch；有 GPU 需自行改镜像 |

**端口**：8000（HTTP）。生产建议前面挂 Nginx 做 TLS 与域名。

## 3. 上线前检查清单

- [ ] 服务器能 `git clone` 本仓库（公开仓库，无需凭证）
- [ ] 准备好 `.env`（见 §5），**至少**填 `JWT_SECRET`、`ADMIN_DEFAULT_PASSWORD`、`USER_RESET_PASSWORD`
- [ ] 准备好模型权重：`checkpoints/<模型ID>/best_ckpt.pt`（**不随仓库分发**）
- [ ] 确认 `ALLOWED_ORIGINS` 填的是真实前端地址，不是 `localhost`
- [ ] 确认 `AGENT_FRONTEND_URL` 指向实际可访问的前端地址
- [ ] 若要用 AI 功能，确认 `LLM_API_KEY` 有效且 `LLM_DAILY_CALL_LIMIT` 合适

## 4. 部署步骤

```bash
# 1) 上传或克隆仓库到服务器
git clone https://github.com/tangfulian/BIT-CD.git /opt/BIT_CD
cd /opt/BIT_CD

# 2) 建 .env
cp .env.example .env
vi .env          # 至少改 §5 标「必填」的三项

# 3) 放权重（不随仓库分发）
mkdir -p checkpoints/BIT_SYSU
scp best_ckpt.pt root@server:/opt/BIT_CD/checkpoints/BIT_SYSU/

# 4) 一键部署
DEPLOY_HOST=<服务器IP> bash deploy.sh
```

`deploy.sh` 依次做四件事：

1. 装 Docker（已装则跳过）
2. 克隆或 `git pull` 到 `/opt/BIT_CD`
3. 校验 `.env` 存在 —— **不存在直接退出**（不会带着默认密钥上线）
4. `docker compose up -d --build`

> **首次部署的两个必踩坑，已在脚本里堵上**
>
> - `data/blackland.db` 在宿主机上不存在时，Docker 的绑定挂载会把它建成**目录**，
>   SQLite 打不开、容器无限重启。现在 `deploy.sh` 会先 `touch` 出空文件。
> - `logs/` 未挂载时，日志写在容器里，一次 `--build` 就全没了。现已挂载。

## 5. 配置项

全部通过 `.env` 注入。**加粗为必填或必须改**。

| 变量 | 默认 | 说明 |
|---|---|---|
| **`JWT_SECRET`** | 随机生成 | 不设则每次重启后所有人需重新登录 |
| **`ADMIN_DEFAULT_PASSWORD`** | 随机生成 | 仅首次初始化数据库时使用 |
| **`USER_RESET_PASSWORD`** | 随机生成 | 管理员重置用户密码时的默认值 |
| `LLM_BASE_URL` | `https://api.deepseek.com` | 换服务商只改这里 |
| `LLM_API_KEY` | 空 | **缺失时 AI 功能直接报「未配置」，不会静默指向别家** |
| `LLM_MODEL` | `deepseek-v4-flash` | 文本用途：分类、报告、定损草稿 |
| `LLM_AGENT_MODEL` | 跟随 `LLM_MODEL` | Agent 需**同时**支持视觉与 Function Calling |
| `LLM_DAILY_CALL_LIMIT` | `500` | 每日调用次数上限，0 = 关闭 |
| `AMAP_WEB_KEY` | 空 | 逆地理编码；缺失时地图降级为空白，其余功能正常 |
| `ALLOWED_ORIGINS` | localhost 系列 | 生产必须改成真实域名 |
| `AGENT_FRONTEND_URL` | `http://localhost:8000` | Agent 将要操控的地址 |
| `AGENT_BROWSER_HEADLESS` | `true` | 生产保持 true |
| `DATABASE_URL` | `sqlite:///./blackland.db` | compose 里已强制 SQLite |

**前端的高德 Key 是另一处**：`frontend/js/config.local.js`（不入库）。
缺失时地图页会显示降级提示，不影响其它功能。

## 6. 上线后验证

### 6.1 两级验证的区别

| | 已验证（本地等效） | 待你在服务器上验 |
|---|---|---|
| 内容 | 干净代码树能否启动、接口是否通、业务链是否跑得通 | 真实服务器上的容器、端口、域名、HTTPS |
| 证据 | 见 §6.2 与 [测试报告](测试报告.md) §6.2 | 需填写 §7 |
| 局限 | **没有在真实服务器上跑过 Docker 部署**（本机无对应环境） | — |

### 6.2 本地已完成的等效验证

从 `HEAD` 导出一棵只含被跟踪文件的树（无 `.env`、无权重、无数据集、无数据库），
启动 uvicorn 后：

| 检查 | 结果 |
|---|---|
| 进程启动 | ✓ |
| `/`、`/index.html`、`/js/main.js` | 200 |
| `/detect/models`、`/captcha`、`/status` | 200 |
| 缺失的前端本地配置 `/frontend/js/config.local.js` | 404（符合预期） |
| 启动告警 | 仅三项未配置项，均自动生成随机值并提示 |

### 6.3 服务器验证清单（按顺序执行）

```bash
# 1. 容器状态：应为 Up，不是 Restarting
docker compose ps

# 2. 启动无异常（看有没有 Traceback）
docker compose logs --tail 80

# 3. 三个基础端点
curl -s -o /dev/null -w "首页      %{http_code}\n" http://127.0.0.1:8000/
curl -s -o /dev/null -w "路由表    %{http_code}\n" http://127.0.0.1:8000/openapi.json
curl -s http://127.0.0.1:8000/status | head -c 200; echo

# 4. 模型清单：确认预期模型 available=true
curl -s http://127.0.0.1:8000/detect/models

# 5. 全量接口冒烟（会创建并删除自己的测试记录）
python scripts/smoke_test.py | tee /tmp/smoke.log
grep -q "0 failed" /tmp/smoke.log && echo "冒烟通过" || echo "冒烟失败，见 /tmp/smoke.log"
```

> `smoke_test.py` 只打印统计、**不设退出码**，所以要用 `grep` 判结果。
> 它会在跑完后删掉自己造的记录，但 `DELETE /history` 是**清空全部**语义 ——
> 在已有真实数据的库上跑之前先看清楚。

**人工确认（浏览器）**：

- [ ] 能打开首页并登录
- [ ] 地块页地图出图（卫星影像）
- [ ] 单张检测能跑通并出结果
- [ ] 检测地图上有数据点
- [ ] 数据看板图表不空白
- [ ] 暗色 / 英文切换正常

## 8. 回滚方案

**当前是全量替换部署，没有灰度与蓝绿。** 回滚 = 回到上一个提交再重建：

```bash
cd /opt/BIT_CD
git log --oneline -5                 # 找到上一个稳定提交
git checkout <上一个提交的 SHA>
docker compose up -d --build
```

数据库回滚需要手工处理：

```bash
# 升级前备份（建议每次上线前都做）
cp data/blackland.db data/backup-$(date +%F).db

# 回滚时恢复
cp data/backup-<日期>.db data/blackland.db
```

> **风险**：如果新版本跑过 Alembic 迁移（加表/加列），旧代码可能不认新结构。
> 回滚前先确认 `alembic current` 与旧代码期望的版本一致。

## 9. 日常运维

| 事项 | 做法 |
|---|---|
| 看日志 | `docker compose logs -f`（容器标准输出）或 `tail -f logs/app.log`（应用日志，5 MB 轮转 3 份） |
| 健康检查 | `curl -s localhost:8000/status`，关注 `uptime` 与 `requests` 计数 |
| 清理孤儿文件 | `python scripts/clean_results.py`（只读预览）；确认后加 `--delete` |
| 更新代码 | `git pull && docker compose up -d --build`（改了 `frontend/`/`backend/` 只需 `docker compose restart`） |
| 备份 | 至少备份 `data/blackland.db` 与 `uploads/`；`results/` 可重算 |
| 改前端后 | **必须把 `frontend/sw.js` 的 `CACHE_NAME` +1**，否则用户浏览器缓存不刷新 |

**注意**：`frontend/`、`backend/`、`alembic/` 是**挂载**进容器的（只读）。
改代码只传文件 + `docker compose restart` 即可，不必重建镜像（重建一次十几分钟，
主要花在装 torch）。但**新增 Python 依赖必须重建**。

## 10. 已知限制与风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **全量替换部署** | 无灰度，出错即全站不可用 | 上线前备份 + 选择低峰期；后续可加健康检查门禁 |
| **SQLite 单文件** | 并发写有锁竞争；单点故障 | 中小规模够用；需要时切 PostgreSQL（`DATABASE_URL`） |
| **无监控告警** | 故障不能第一时间发现 | 目前只能靠 `/status` 与日志；
建议外挂 uptime 监控 |
| **无自动备份** | 误删/磁盘损坏即丢数据 | 建议 cron 每日 `cp data/blackland.db` |
| **权重不随仓库** | 新服务器上模型全不可用 | 部署前必须单独传 `checkpoints/` |
| **CPU 推理较慢** | 大批量检测耗时明显 | 有 GPU 时改用 CUDA 版 torch 重建镜像 |
| **Agent 拉起 Chromium** | 占内存；已用 `init: true` 回收僵尸进程 | 内存不足时关掉 Agent 或调小 `AGENT_MAX_STEPS` |
| **LLM 外部依赖** | 限流/欠费会导致 AI 功能失败 | 有每日预算闸；失败时给出明确错误而非静默降级 |
