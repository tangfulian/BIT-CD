# 工程经验

这些条目都来自一个真实项目（FastAPI + 原生 JS + PyTorch 的遥感检测系统）的开发过程，
每一条都是**踩过一次之后才写下来的**，不是通用说教。写法尽量与具体业务无关，
可以直接搬到别的项目。

顺序按类别，不按重要性。

---

## 一、验证：怎么确认一件事「真的成立」

### 1. 测试通过 ≠ 功能正确

一次依赖升级后 178 个用例全绿，但线上第一次推理卡住 5 分钟。原因不在被测代码里，
而在启动路径上 —— 测试根本没走那条路。

**教训**：绿灯只说明「用例覆盖到的部分没坏」。改动碰到启动、部署、外部依赖时，
测试给不了保证，必须真跑一次。

### 2. 「双语都验过」其实全程验的是中文

前端按 `localStorage['lang']` 设置语言，而 i18n 模块读的是 `app_lang`。
键名写错，语言从未切换过，于是「英文模式无残留」的结论是假的 —— 连续几轮都是。

**教训**：验证脚本里每一个「设置」，都要确认它真的生效了。最省事的做法是
在断言里先验一次状态（例如断言页面上确实出现了英文单词），再验你要验的东西。

### 3. 断言太弱会放过 bug

筛选功能的检查写成「筛完之后条数 > 0」，结果「13 → 13」也照样通过。
真正的原因是下拉框**根本没有绑定 change 事件**。

**教训**：断言要卡在「行为改变」上，不是「没有崩」。能写成相等就别写大于。

### 4. 第一次测出来的问题，先复测两次再下结论

「移动端横向溢出 16px」报了两次，第三次测是 0 —— 那是抽屉动画进行中的瞬态。
反过来也成立：偶发的失败不要归因为 flaky，先把复现条件找出来。

**教训**：一次测量是一个样本，不是结论。

### 5. 批量改完，必须数一遍实际改了几处

用正则给表单控件补 `for` 属性，写完之后一数：改了 0 处。原因是正则忘了匹配
label 里的文字和结束标签。

**教训**：批量操作的正确性检查是「数出来的数对不对得上预期」，不是「脚本没报错」。

### 6. 生成的图片/素材要打开看一眼

分享卡片第一次生成出来，右半边几乎全黑（掩膜图本身是大面积黑色）。
只看脚本输出「saved 1200x630」是发现不了的。

**教训**：视觉产物必须打开看。文件存在、尺寸正确、字节数正常，都和「好看」无关。

### 7. CI 红了，先确认是哪一步红的

两次失败都以为是测试挂了，实际一次是 pytest 没装（测试其实从没跑过），
一次是 `ruff` 的两个未使用导入。

**教训**：读失败步骤名，别读结论。

## 二、改代码

### 1. 按区间替换会删掉你没看见的东西

给 `main.py` 加一段启动逻辑，用「从 A 到 B 整段替换」的方式改，把夹在中间的
三个路由注册一起删了。表现是登录接口 404，直到浏览器跑测试冒出两个 404 才发现。

**教训**：注册表、清单、配置这种地方，永远用「在锚点前后插入」，不要用区间替换。
改完 `git diff` 必须逐行看完，尤其是删除行。

### 2. `from X import y` 会让打桩失效

测试里 `monkeypatch.setattr("模块A.func", 假函数)`，但被测代码写的是
`from 模块A import func`，拿到的是导入时的引用 —— 桩打不上，测试仍然「通过」。

**教训**：打桩要打在**使用方查名字的那个命名空间**上。测试里留一个「数值刻意不同」
的探针，如果桩失效，断言会立刻失败，而不是静默走真实实现。

### 3. 缓存键必须包含所有影响输出的输入

检测缓存键是（影像、模型、阈值、用户），但记录上还写了地名、变化类型、
前后时相、所属序列。于是同一对影像换个地块再跑一次，拿回来的是**旧记录**，
上面挂着上一个地块的县名。

**教训**：问一句「这两个请求的输出会不会不同」—— 会不同就必须进键。
纯描述性字段可以命中后覆盖，但「归属」类字段（挂在哪个序列/项目下）应该进键。

### 4. 死代码会伪装成功能

一个「删除单条记录暂未开放」的提示文案一直留在语言包里，而删除功能早就上线了；
一个「跨刷新恢复队列」的持久化逻辑还在，但队列已经搬到服务端了。

**教训**：功能搬家时，旧路径要么删、要么写清楚为什么留。留着不说，
下一个人会以为它还在工作。

### 5. 外部文本一律 `textContent`，不要拼 `innerHTML`

论文标题、用户名这类外部数据进 DOM 时，用 DOM API 逐个构造节点。
拼字符串的话，标题里一个 `<` 就能变成标签。

**教训**：`innerHTML` 只用于完全由本项目控制的静态模板。

### 6. 手抄一份逻辑，抄的时候就会少抄一行

一个页面为了保证多样性，把主流程「抄」了一份，结果漏掉了概率图落盘那一步，
导致这条路径产生的记录永远缺一个字段，在三条下游功能上全被拒。

**教训**：编排逻辑要么复用，要么下沉成共享函数。复制粘贴的代价会在几周后结算。

### 7. 语言/资源文件少一个逗号，整个前端会白屏

给语言包补三个键，插入位置少了一个逗号 → 模块解析失败 → 整张模块图加载失败。
而基于正则的键一致性检查**照样报 ✓**，因为它不解析 JavaScript。

**教训**：静态检查要覆盖「能不能被解析」，不只是「内容对不对」。
ES module 可以用 `node --check`（先复制成 `.mjs`，否则会按 CommonJS 报错）。

## 三、环境与工具

### 1. 本地没装的工具，问题只会在 CI 暴露

本地跑不了 `ruff`，于是两个未使用导入一路进了提交。装上之后
`ruff check .` 十秒出结果。

**教训**：CI 里跑的检查，本地要么也跑，要么在提交前明确知道「这一项我没验」。

### 2. 测试不能依赖本地配置

一条断言「默认未配置」的用例，在配了真实凭据的开发机上必然失败。

**教训**：测试里凡是被测行为依赖环境变量，就用 `monkeypatch` 显式设定，
不要依赖「我这台机器上刚好没配」。

### 3. 建表与迁移会打架

测试用 `create_all` 建表，应用启动又跑一次迁移。迁移版本表（`alembic_version`）
不在 ORM 的元数据里，`drop_all` 删不掉它 —— 于是「库已是最新」的判断成立，
迁移在已存在的表上重放，撞 `table already exists`。迁移头部不动的时候不会暴露，
一加新迁移就必现。

**教训**：测试里要显式处理迁移版本表；任何「两套建表机制」并存的地方，
都要想清楚谁说了算。

### 4. `docker compose restart` 不重读 `env_file`

改完 `.env` 后重启，容器里的环境变量还是旧的。必须 `up -d` 重建容器。

**教训**：环境变量属于「容器创建时」的状态。改配置要重建，不是重启。

### 5. 绑定挂载的源不存在，Docker 会给你建一个目录

`./data/app.db:/app/app.db` —— 宿主机上文件不存在时，Docker 建的是**目录**，
应用打开数据库直接崩，容器无限重启。

**教训**：部署脚本里先 `mkdir -p` / `touch` 把挂载源造出来。

### 6. 管道会吞掉退出码

`if git push | tail -3; then` 判断的是 `tail` 的退出码，永远为 0。
推送明明失败，脚本报成功。

**教训**：任何「结果判断」都要拿到真实进程的退出码（重定向到文件再看 `$?`，
或开 `set -o pipefail`）。

## 四、外部依赖

### 1. 先探测，再设计

要做「最新资讯」模块，先逐个探测数据源：一个返回 418 拦爬虫、一个 12 秒超时、
一个没有订阅源、一个 `/rss` 是 404 —— 最后只有一家提供稳定的结构化 API。
如果先按「抓网页」设计，功能上线一周就会被页面改版打断。

**教训**：依赖外部数据的功能，可行性是探测出来的，不是查文档查出来的。
而且要在**部署环境**里探测 —— 本机能访问不代表服务器能。

### 2. 官方源在国内可能慢三个数量级

同一个包，官方源 1.6 KB/s，镜像 28 MB/s。构建卡了 49 分钟，CPU 只用了 10 秒。

**教训**：把下载源做成可覆盖的参数，默认保持官方；同时在文档里写清楚
「国内构建建议覆盖成什么」。

### 3. 外部数据取不到时，退回旧缓存

列表拉取失败就清空，用户看到的是「系统没有数据」，而不是「暂时取不到」。

**教训**：区分「空」和「失败」。有旧数据就用旧数据，并把「这是缓存」标出来。

## 五、部署

### 1. 部署前先备份，一条命令就能回滚

每次都打一份 `backend/ frontend/ alembic/ .env` 的 tar，文件名带时间戳。

**教训**：备份的成本是几秒钟，没有备份时排障的成本是几十分钟。

### 2. 部署后必须验，而且要验到「行为」这一层

只验 HTTP 200 没有意义。要验：迁移版本号、新接口的鉴权语义（401 而不是 404）、
新表存不存在、后台线程有没有启动、以及**真实跑一次业务**。

**教训**：部署完成的定义是「线上跑通了一条真实链路」，不是「容器起来了」。

### 3. 静态文件是挂载的，后端代码不是

前端改完传文件加刷新就生效；后端改完必须重启进程。
两类改动混在一次部署里时，容易漏掉后者。

**教训**：部署清单里分开写「需要重启的」和「不需要的」。

## 六、产品与交互

### 1. 陌生人看到的第一屏，决定他留不留

一个功能完整但**没有首屏**的系统，访客打开看到的是一个空表单和 14 个带锁的菜单项。
加了一句话价值 + 一张成果图 + 一个「用示例试一次」之后，路径才通。

**教训**：功能页回答「怎么做」，首屏回答「为什么值得做」。两件事不能混。

### 2. 空状态要给出下一步

「还没有检测结果」是描述，不是引导。加一句「没有影像？用示例试一次」，
转化路径就短了一半。

**教训**：每个空状态都问一遍「用户此刻的下一步是什么」。

### 3. 额度/限流放在服务端

前端算的「剩余 N 次」清个缓存就归零，直接打接口更是完全不受约束。

**教训**：任何「限制」只要服务端不认，就不是限制。前端那份只能当**显示**用。

### 4. 一组失败不该拖垮一整批

批量任务里一张坏图让整批 500，前面成功的也白跑。

**教训**：批处理要逐项 try/catch，把失败记在那一项上，然后继续。

### 5. 取消要协作式，不要硬杀

直接杀线程会留下半截的数据库记录和孤儿文件。置一个标志位，
让执行者处理完当前这一项再停。

**教训**：中断状态要能被读到、能被恢复，不是「消失」。

### 6. 进程重启不能丢任务

停机时停在「运行中」的任务，重启后会永远停在那里 —— 界面上是一个不动
的进度条。启动时把它们退回队列。

**教训**：任何「有状态的后台工作」，都要回答「重启之后怎么办」。
重跑是否安全取决于下游是否幂等（这个项目里靠影像哈希去重）。

### 7. 领任务要原子

「先查再改」在两个 worker 同时启动时会把同一批跑两遍。

**教训**：认领动作写成带条件的 UPDATE（`WHERE status='queued'` 并检查影响行数）。

## 附：一条元经验

**把「我怎么知道这是对的」写进提交信息。**

这个项目的提交信息里，凡是写了「实测 … 得到 …」「验证方式：…」的改动，
后面几乎没再返工；只写了「修好了 XX」的，有几处后来又被打回。

因为写下验证过程时，你会立刻发现自己其实没验。
